# Post-Signup Telegram Screen — Design

Date: 2026-07-21
Status: Approved (design); pending implementation plan

## Summary

Make `apps/landing/src/app/link/page.tsx` — which already implements the
full "connect Telegram" flow (deep link, open, poll, confirm) — the actual
destination a new user lands on right after signup, instead of the small
dismissible banner currently buried in the dashboard's account tab. Add a
QR code alongside the existing "Open Telegram" button so a desktop user
can scan with their phone instead of needing Telegram Desktop installed.

This is the smaller of two sub-projects bundled together in this planning
cycle (the other, custom MCP servers, has its own spec:
`docs/superpowers/specs/2026-07-21-custom-mcp-servers-design.md` — the two
are otherwise unrelated and can ship independently).

## Scope (v1)

- **In scope:** changing `signup/page.tsx`'s post-auth destination,
  pre-fetching the Telegram deep-link token on page load instead of on
  button click, adding a client-side-rendered QR code to `/link`'s initial
  state.
- **Out of scope:** redesigning `/link`'s visual style beyond adding the QR
  code (it already matches the app's existing look), a token-refresh
  mechanism for the 15-minute expiry (accepted limitation, see below),
  removing or changing the dashboard's existing `showWelcome` banner (it
  still fires correctly for anyone who reaches `/dashboard?welcome=1`
  directly or via an old bookmark — just no longer the primary path).

## Current state (why this is mostly wiring, not new UI)

`/link` already:
- Calls `POST /api/gateway/telegram/token` to get a one-time
  `{ token, deepLink }` (`https://t.me/<bot>?start=<token>`, 15-minute
  expiry, generated by `gateway-runner.ts`'s `createTelegramLinkToken`).
- Opens that link, polls `GET /api/gateway/connections` every 2s (up to
  90s) for a `platform: "telegram"` entry.
- Shows three states: initial ("Connect Telegram"), waiting ("Waiting for
  Start"), and connected (success + "Go to Dashboard").
- Already handles a user who's already linked (checks on mount, jumps
  straight to the connected state) — so making this the signup callback
  is safe for any future edge case where auth redirects here again.

`signup/page.tsx` currently sets `callbackURL="/dashboard?welcome=1"`,
which lands on the dashboard's account tab and shows a small dismissible
banner ("Welcome to Yomi! Connect Telegram or an integration...") — no
button, no QR code, easy to miss.

## Design

### 1. Change the signup destination

`apps/landing/src/app/signup/page.tsx`:

```tsx
<AuthCard defaultMode="signup" callbackURL="/link" />
```

(was `callbackURL="/dashboard?welcome=1"`)

### 2. Pre-fetch the deep link on mount

`apps/landing/src/app/link/page.tsx`'s `LinkPageContent` currently only
calls the token endpoint inside `handleConnect` (the button's `onClick`),
using a `window.open("about:blank", "_blank")` placeholder-then-redirect
trick specifically to dodge popup blockers (a `window.open` call must be
synchronous within a user gesture). Pre-fetching removes the need for that
trick entirely — once `deepLink` state is already populated before the
click, `window.open(deepLink, "_blank")` can be called directly inside the
click handler, which is *more* popup-blocker-safe than the current
about:blank workaround, not less.

Add a fetch-on-mount effect (parallel to the existing
`checkTelegramLinked` effect):

```ts
useEffect(() => {
  if (!session || connected) return
  void fetch(`/api/gateway/telegram/token`, {
    method: "POST",
    headers: { Authorization: `Bearer ${session.session.token}` },
  })
    .then((res) => res.json() as Promise<{ deepLink?: string }>)
    .then((data) => {
      if (data.deepLink) setDeepLink(data.deepLink)
    })
    .catch(() => {
      // best-effort — the button's own click handler still works as a fallback
    })
}, [session, connected])
```

`handleConnect` (the button handler) is simplified to reuse `deepLink` if
already set, only hitting the token endpoint itself as a fallback if the
mount-time fetch hasn't resolved yet or failed.

### 3. QR code

New dependency: `qrcode.react` (client-side SVG generation via its
`QRCodeSVG` component — **not** a third-party QR-image API). The deep link
carries a one-time auth token in its `?start=` parameter; sending that URL
to an external image-generation service would hand the token to that
third party over the network, who could then race the real user to
consume it. Client-side generation never sends the token anywhere it
isn't already going.

Rendered next to the existing "Connect Telegram" button in the initial
(not-yet-connected, not-yet-waiting) state, once `deepLink` is populated:

```tsx
import { QRCodeSVG } from "qrcode.react"

// ...

{deepLink && (
  <div className="flex flex-col items-center gap-2">
    <QRCodeSVG value={deepLink} size={120} />
    <p className="text-xs text-muted-foreground">Or scan with your phone</p>
  </div>
)}
```

### 4. Accepted limitation: token expiry

The token expires in 15 minutes. If a user leaves this page open without
interacting that long, the deep link/QR both go stale (Telegram would
report an invalid/expired `/start` token). No refresh-on-expiry handling
in v1 — 15 minutes is generous for "right after signup," and the button's
`handleConnect` fallback already re-fetches a fresh token on click if
`deepLink` is empty or the pre-fetch failed, which naturally recovers most
cases (a stale pre-fetched link only matters if the user waits 15+ minutes
*and* only ever uses the QR code, never clicking the button).

## Testing

No automated test — this is a client-rendered Next.js page with no
existing test harness in `apps/landing` (confirmed across two prior
features this session). Verify with typecheck + lint, then a manual
signup-flow walkthrough, which needs a real backend/DB connection this
sandbox doesn't have (same limitation noted in the two prior specs this
session) — flag to the user at implementation time rather than silently
skipping it.
